# Pilot notes: FlutterFlow → Claude Code PWA

Observations that matter for deciding whether the office moves its mobile apps.
One dated line per item. Tag each one: [agent], [ios], [deploy], [tooling], [spec].

- 2026-11-01 [spec] Docs written for one backend carry leftovers after a stack change: data-model.md still describes Firestore collections, offline persistence, and Cloud Functions after the move to Postgres. The agent treats docs as instructions, so stale storage advice is a real hazard. Budget a doc-cleanup pass when changing stacks. (Fixed the same day: entities made storage-neutral, offline rewritten for IndexedDB + outbox, tie rule moved to open, schema checks added to database.md.)
- 2026-11-01 [tooling] The dev machine had no Node.js (and no Python), so the first npm step failed before anything ran. It was installed mid-task via `winget install OpenJS.NodeJS.LTS` (v26.13.0), and agent shells needed PATH patched by hand until restarted. Add "Node LTS + Docker Desktop installed" to the machine-setup checklist for any office repo.
- 2026-11-01 [spec] Postgres gotcha caught by a pgTAP test: in `select court_end::text ... order by inning, court_end`, the ORDER BY binds to the text-cast output column and sorts north before south. Play-order queries must sort on the enum column itself (qualify it, or don't alias over it).
- 2026-11-01 [agent] Initial DB migration (one prompt, ~45 min, 52 pgTAP tests passing): strong result, no defects found in planner review. Good habits seen: asked before installing Node instead of improvising; named every constraint so tests prove the *intended* rule fired, not just "some error"; checked on its own that RLS (not missing grants) was what blocked anon; listed its own deviations from the brief. Gap: seed data the DB doesn't validate (ringer combos) still needed a human/planner check (all 18 frames were valid).
- 2026-11-01 [tooling] `npm install typescript` now resolves to TypeScript 7 (the native compiler), which svelte-check doesn't support yet (peer `^5 || ^6`), so the install failed with ERESOLVE. Pinned `typescript@^6`. Expect this kind of version skew whenever a core tool has just had a major release.
- 2026-11-01 [tooling] `npm audit` reports moderate advisories in build-time deps (workbox-build -> deepmerge/glob, via vite-plugin-pwa). The only "fix" is downgrading vite-plugin-pwa a major version. None of it ships to the browser; left as is, worth re-checking before release.
- 2026-11-01 [agent] Task 3a (scaffold + domain logic, one prompt): 135 unit + 6 browser tests, no defects in planner review. Agent mutation-tested its own test suite unprompted, caught a faux-bold font issue the prototype had, and handled a fresh TypeScript 7 / svelte-check incompatibility by pinning and documenting it. So far the agent is reliable on logic when the spec is precise; the open pilot question moves to UI fidelity (3b).
- 2026-11-01 [spec] The prototype's DS stylesheet overrides every `.btn` to square corners (the "blueprint" direction CLAUDE.md says to ignore), so buttons without an inline radius render square, e.g. Confirm & Next. "Match the rendered look" and "ignore blueprint" pull opposite ways there; the app keeps rounded corners. Similarly, its buttons are 30-38px tall, under CLAUDE.md's 44px rule, so the app's are taller. Worth saying up front which rule wins when the reference and the house rules disagree.
- 2026-11-01 [tooling] Visual comparison against the prototype works: Playwright can drive the prototype's own runtime and the app through the same steps for screenshot pairs. It needs network (the prototype pulls React/Babel from unpkg) and must be served over http, not file://. Cheap and worth repeating each UI step.
- 2026-11-01 [agent] Task 3b (three screens, one prompt, ~12 min agent time): planner compared all 7 prototype/app screenshot pairs independently. Fidelity is near pixel-level, and the agent's own list of differences was ACCURATE and complete — the opposite of the FlutterFlow agent, whose "verified" meant "compiles" and whose scoring screen didn't run. Differences found were all deliberate and justified (44px tap targets, 16px inputs, spec over prototype). Key enabler: making the agent screenshot the reference and its output side by side, so claims are checkable. Recommend this as a standard step for UI work at the office.
- 2026-11-01 [deploy] Setting wrangler's `compatibility_date` to "today" broke `wrangler dev`: the local runtime bundled with wrangler 4.156 only supports dates up to 2026-10-30, two days earlier. Use a date the installed wrangler supports, not the calendar date. Also: Cloudflare matches `_headers` by request path, so a rule for `/index.html` doesn't cover `/`, and `/index.html` itself 307-redirects to `/`. Vite-plugin-pwa also emits an unhashed `/registerSW.js` outside `/assets` that needs no-cache. Check the real dist/ before writing cache rules.
- 2026-11-01 [deploy] First Cloudflare deploy (Workers static assets via Workers Builds, GitHub-connected): succeeded on the first try, ~40 s from build start to live URL (https://ringer.jdtornado.workers.dev). Josh's setup was a few minutes of dashboard clicks. Node 26 picked up from .node-version. Contrast with the old model: no server to provision, every push to main is a deploy, rollback is a dashboard click. Notes: the build image runs npm 10.9 (local is 11) and blocks dependency install scripts (esbuild, workerd) by default; harmless today, the first suspect if a build ever fails on a missing native binary.
- 2026-11-01 [android] Real-device test on Josh's Android phone (Chrome) passed the full checklist: install, standalone launch, resume after the app is killed, offline launch, reduced motion, no console errors. Zero Android-specific fixes needed. iOS checklist still OPEN, pending someone with an iPhone: manual Add to Home Screen, apple-touch-icon, standalone status bar/safe areas, Safari vs home-screen app storage separation, 7-day storage eviction, Reduce Motion. Hold the office decision until it's run.
- 2026-11-01 [tooling] Switching the service worker from autoUpdate to a user prompt: vite-plugin-pwa's `updateSW(true)` sent skip-waiting but never reloaded the page when the update had been found by our own `registration.update()` call. Workbox reports such an update as "external", and the helper only reloads on its own updates. The app sat on the old version. Fixed by reloading on `controllerchange`; a two-build Playwright test (serve v1, switch the server to v2, trigger the check) caught it. Testing update flows needs a real second deploy, not mocks. The Workers Builds env var `WORKERS_CI_COMMIT_SHA` was confirmed in Cloudflare's docs.
- 2026-11-01 [deploy] First branch push failed its Cloudflare preview build. Cloudflare had silently enabled branch previews for the new Worker (a dashboard pop-up, no setting shown) using `npx wrangler preview`, an OPEN BETA command that refuses to run without a `"previews": {}` block in wrangler.jsonc. Nothing in the setup flow mentioned it; only the build log did. Also, GitHub's check said "failed in 0s" when the build had actually run ~40 s, so read the Cloudflare log, not the GitHub summary. Lesson for the office: platform defaults move fast, so budget for config surprises on the first use of each deploy path (production, preview), and always read the full build log.
- 2026-11-01 [deploy] Branch → preview → fast-forward merge → production works end to end. Production uploaded ZERO new files: the fast-forward merge made main the exact commit the preview had already built, so production shipped byte-for-byte what was tested on the preview URL. That's a strong argument for a fast-forward-only (or rebase) merge policy at the office. Explicit workers_dev/preview_urls cleared both build warnings. Each branch preview is its own origin (separate install and storage), so testing never touches a real in-progress game.
